# cc-hardness 项目全景与面试讲解

## 1. 一句话定位

cc-hardness 是一个本地优先的多智能体软件研发编排平台。它本身不训练或托管大模型，而是把 Claude Code CLI 当作“执行工作单元”，由 Go 控制面根据可编辑 DAG 调度产品、架构、UI、前端、后端、测试和交付等角色，在同一个任务目录内完成软件研发并保留全过程状态与产物。

最准确的架构概括是：**模块化单体控制面 + 多个持久 Claude Code 子进程 + 文件型任务工作区 + 人工确认门禁**。

## 2. 项目真正解决的问题

普通 AI 编程对话主要解决“当前这一轮怎么写代码”，cc-hardness 解决的是更上层的问题：一个完整软件项目由谁做、先做什么、哪些工作可以并行、什么时候必须等用户确认、不同角色如何共享上下文、异常后如何继续，以及最终产物如何被部署和验收。

因此它的核心不是聊天界面，而是四项能力：

1. 资产管理：管理 Agent、Skill、Rule、Knowledge Base 和环境配置集，并保留版本。
2. 任务编排：把研发过程建模为团队成员和 DAG 节点，校验依赖、角色和状态。
3. 运行时管理：为不同任务成员启动或复用 Claude Code 长生命周期进程，收发 NDJSON 协议事件。
4. 过程治理：通过需求、架构、原型和交付确认点控制阶段推进，并把状态、对话和产物保存在任务目录中。

## 3. 总体分层

### 3.1 React 桌面 Web 控制台

前端是用户的操作面，负责任务列表、资产管理、团队编辑、DAG 展示、阶段切换、成员对话、历史会话、文件查看和最终部署入口。

前端不直接修改任务文件，也不直接管理 Claude 进程。所有业务事实都通过 Go API 读取或提交。活动会话的输出按序号每 250ms 增量轮询；团队组建阶段大约每 3 秒刷新计划修订；运行阶段大约每 4 秒刷新任务与 DAG 状态。当前没有使用 WebSocket。

### 3.2 Go 模块化单体控制面

Go 后端运行在能访问本地项目目录和 Claude Code CLI 的宿主机上，内部按职责分成：

- HTTP API：把页面动作映射为 REST 命令和查询，同时托管生产版前端静态文件。
- Catalog/ConfigSet：管理全局智能体、技能、规则、知识库和环境配置。
- Task Service：负责任务生命周期、团队方案、DAG 校验、阶段推进、变更记录和部署。
- Task Repository/FileData：把领域对象映射到目录、JSON、JSONL 和 NDJSON 文件。
- Runtime Manager：管理 Claude Code 子进程、stdin/stdout/stderr、会话复用、事件序号和停止行为。

它是模块化单体，不是微服务。原因是首版所有关键资源——状态文件、项目目录和 CLI 进程——都在同一台宿主机，放在一个进程内更容易保证顺序、锁和资源生命周期。

### 3.3 Claude Code 多会话运行面

每个任务成员拥有独立的会话路由。后端以任务根目录作为工作目录启动 Claude Code，并使用 `stream-json` 输入输出协议。不同角色的上下文互相隔离，但它们读写同一个任务目录，因此通过上游文档、源码、配置快照和任务状态完成协作。

“多智能体”在这里不是一个模型内部的多 Agent 框架，而是**多个受控制面管理的 Claude Code CLI 进程**。

### 3.4 文件型持久化与共享工作区

`data/catalog` 保存全局复用资产，`data/config` 保存配置集，`data/tasks/{task-id}` 既是任务数据目录，也是所有 Agent 共同工作的项目目录。

一个任务目录包含三类内容：

- 业务事实：任务元数据、团队计划、DAG 定义、运行状态、变更请求和交付信息。
- AI 运行材料：固定版本的 Agent、Skill、Rule、知识库清单、配置集快照和协议日志。
- 项目产物：用户输入、PRD、架构文档、UI 文档、前后端源码、测试报告和交付文档。

小型当前状态使用 JSON；变更等追加历史使用 JSONL；Claude 输入、输出和事件使用 NDJSON。关键 JSON 通过“同目录临时文件 + 刷盘 + 原子替换”写入，避免读到半份文件。

## 4. 服务启动流程

1. 读取监听地址、数据目录和前端静态目录，默认只监听本机地址。
2. 创建 Catalog、配置集和 Task 仓储所需目录。
3. 启动时安装或补齐平台内置的角色、技能和规则。
4. 装配 Task Service、Runtime Manager 和 HTTP Handler。
5. 启动 Go HTTP Server；退出时先停止所有 Claude 会话，再优雅关闭 HTTP 服务。

这里没有数据库迁移、消息队列连接或远程模型服务启动，部署依赖相对少。

## 5. 从新建任务到最终交付的完整主流程

### 5.1 创建任务工作区

用户填写任务名称、背景、任务组并上传材料。后端生成不可变任务 ID、预分配一对本地前后端端口，建立任务目录骨架，然后写入初始 `task.json`。初始状态是 DRAFT/PLANNING。

上传文件只允许进入当前任务的 `inputs` 目录，单文件受请求大小限制。

### 5.2 生成团队和初始 DAG

当前实现并不是先让 AI 从零推理出团队。后端首先按固定角色模板装配项目经理、产品经理、架构师、UI、前端、后端、测试和审计/交付成员，再生成一条默认全栈研发 DAG。任务构建智能体随后可以通过专用 API 增减成员、修改能力或重构工作流。

计划保存前会校验：

- 必须且只能有一个项目经理，项目经理不可删除。
- 成员 ID 唯一，成员引用的 Agent 版本、Skill、Rule、知识库和配置集必须存在。
- 节点 Key 唯一；Agent 节点必须引用有效成员。
- 依赖只能指向存在的节点，DependencyMode 只能是 ALL 或 ANY。
- DAG 不允许形成环。

成员移除时，系统不只是删节点，还会把下游节点对已删除节点的依赖展开为该节点最近的存活前置依赖，从而尽量保持工作流连通。

### 5.3 用户确认团队并启动任务

用户点击进入下一步后，后端再次校验计划，并把选定版本的 Agent、Skill、Rule、知识库和配置集物化到任务目录。这样任务运行时使用的是固定快照，不会因全局资产后来升级而无意改变。

随后创建独立的 RuntimeState：无前置依赖的节点变为 READY，其余节点保持 PENDING；任务进入 ALIGNMENT 阶段。后端启动或复用项目经理会话，并自动启动当前可执行的入口节点，通常是产品经理的需求分析。

### 5.4 DAG 如何调度

每个节点包含类型、负责人、阶段、依赖列表、依赖模式、状态和任务说明。节点状态主路径是：

`PENDING → READY → RUNNING → SUCCEEDED / FAILED`

人工节点可以从 READY 进入 WAITING_USER；失败节点允许重试或跳过。一个节点成功或跳过后，调度器扫描所有 PENDING 节点：

- ALL：所有依赖都 SUCCEEDED 或 SKIPPED 才解锁。
- ANY：任意一个依赖成功或跳过即可解锁。

解锁只代表节点可执行。自动启动还要满足阶段边界：当前阶段节点可以启动；显式标记为 Background 的可回退准备节点可以提前启动；原型评审期间，已经通过架构门禁的开发节点也允许并行。具体业务实现不能用 Background 绕过人工确认。

### 5.5 Claude 节点如何执行

调度一个 Agent 节点时，系统先把节点改为 RUNNING，再拼装三层 Prompt：

1. 角色本体：该成员固定版本的 Agent Markdown。
2. 平台上下文：任务身份、工作目录限制、预分配端口、配置快照位置和文档输出规则。
3. 节点指令：当前阶段任务、边界、上游材料和期望产物。

Runtime Manager 优先复用同一任务成员仍在运行的空闲会话；没有可用会话才启动新的 Claude Code 进程。忙碌会话会拒绝新的用户消息，避免两个 Turn 在同一个 stdin 通道交错。

### 5.6 流式事件与节点完成判定

每个会话至少有三条并发执行路径：读取 stdout、读取 stderr、等待进程退出。stdin 另有互斥锁，确保用户消息和控制响应不会混写成损坏的 NDJSON。

stdout 中的可见文本增量被转换为轻量事件供浏览器轮询；完整原始协议仍写入任务日志。每个事件拥有单会话递增序号，因此浏览器只请求 `after=最后序号` 的增量数据。

当 Claude 返回非错误的 `result` 事件时，节点被判定为 SUCCEEDED；错误结果或非预期进程退出会判定为 FAILED。成功后系统继续扫描并启动新解锁节点。Claude 进程不会因为一个节点完成就自动退出，它会保留给该成员的后续对话或后续阶段复用。

### 5.7 人工门禁和阶段推进

默认主流程包含四类人工决策：确认 PRD、确认技术设计、确认原型、最终验收。

点击“下一步”前，当前阶段的所有 Agent 节点必须成功或跳过。推进阶段时，当前阶段的确认节点被归档为成功，后继节点被重新计算并解锁；任务进入 DEVELOPMENT 后，高层状态从 PLANNING 变为 RUNNING。

这个设计把“AI 已经回答完”与“用户认可阶段结果”分开，防止需求、架构或视觉方案未经确认就固化到下游实现。

### 5.8 增量需求和缺陷路由

用户补充需求或测试发现缺陷时，系统先追加一条 ChangeRequest，再把内容路由给项目经理的持久会话。项目经理负责分析影响范围并分派，而不是无条件重跑完整流程。

当前 ChangeRequest 主要是可追踪记录和消息入口；更完整的“自动生成增量 DAG、闭环更新 Change 状态”仍属于可继续加强的部分。

### 5.9 最终验收与部署

交付节点完成后，任务进入 ACCEPTANCE，只有用户显式确认才变为 COMPLETED。完成后才允许部署。

部署器会停止旧部署，选择或校验本机端口，识别 Node 项目或 Maven/Gradle Spring Boot 后端，分别启动前后端进程，把 stdout/stderr 写入部署日志，并等待两个端口真正监听成功后再保存可点击地址和 PID。Vite 项目通过运行时配置覆盖端口和 `/api` 代理，不修改生成项目自己的 Vite 配置。

## 6. 会话与恢复机制

会话有两层状态：

- 内存层：进程句柄、stdin、最近事件、Busy 状态和“任务 + 成员 → 最新会话”的路由。
- 磁盘层：stdin、Claude 原始输出、stderr 和统一事件日志，以及 RuntimeState 中的最新会话 ID。

页面切换不会主动制造一轮隐藏的“请恢复上下文”对话。若后端仍持有活会话，页面直接重连；若 DAG 显示节点仍在 RUNNING，但进程表已丢失，页面会触发节点重新运行。

需要准确说明：**当前不是 Claude 原生会话级断点续传**。Go 服务重启后，旧会话可从磁盘查看历史，但进程管道和模型内上下文不会恢复；系统依赖任务文件和完整 Prompt 启动替代会话。这是“任务级恢复”，不是“同一模型上下文精确恢复”。

## 7. 并发、一致性和资源生命周期

- 计划修改使用进程内互斥锁串行化，成员修改与可选 DAG 替换可以一次提交。
- RuntimeState 的读改写使用独立互斥锁，避免多个并行 Agent 同时完成时互相覆盖。
- 部署、重部署和停止使用部署锁，避免重复点击留下孤儿进程。
- Session 的 stdin 使用写锁，事件集合和 Busy 状态使用读写锁，Manager 的会话索引也有读写锁。
- 内存事件有上限，达到 2000 条后缩减到最近 1500 条；完整原始事件仍在磁盘。
- 任务关闭会停止进程并保留所有文件为只读；任务删除会先停止会话与部署进程，再永久删除整个任务目录。

一致性的边界也要说清：这些锁都是单 Go 进程内锁，当前没有跨进程分布式锁；修订号会递增，但完整计划保存没有做严格的客户端 Compare-And-Swap。系统默认单实例运行，多实例同时操作同一数据目录并不安全。

## 8. 安全边界

已经实现的安全措施包括：默认绑定本机地址、任务 ID 和文件路径校验、文件打开时检查相对路径和符号链接边界、请求体大小限制、JSON 拒绝未知字段、日志与工作区按任务隔离。

必须诚实指出一个重要现状：Runtime Manager 以 `bypassPermissions` 启动 Claude Code，并自动允许收到的工具权限回调。虽然 API 保留了人工允许/拒绝接口，但正常运行策略偏向无人值守全权限执行。因此它只适合受信任的本地任务目录；如果面向多人或不可信仓库，需要改成显式权限策略、命令白名单、沙箱或独立 Worker 隔离。

## 9. 为什么选择这些技术

### Go

难点集中在长生命周期子进程、并发读取 stdout/stderr、stdin 串行写、进程退出清理和状态同步。Go 的 goroutine、context、锁和 `os/exec` 非常贴合，并且方便本地单文件部署。

### React + TypeScript

前端同时承载 DAG、阶段状态、会话流、资产编辑和多个任务页签，React 适合以组件和 Hooks 管理复杂交互；TypeScript 与 Go 的 JSON 模型形成明确契约。

### 文件而不是数据库

优势是零基础设施、可直接检查、任务目录可整体复制归档、Agent 天然能读写。代价是复杂查询、事务、并发、多实例和大规模数据能力弱。因此它适合当前“本地单用户研发控制台”的定位，不适合直接扩成大规模 SaaS。

### REST 轮询而不是 WebSocket

首版实现简单、断线后可按序号补拉、容易调试。代价是频繁请求和实时性上限；多用户或高事件量场景可以在不改变事件序号模型的前提下升级为 WebSocket/SSE。

## 10. 当前实现与理想设计的差距

1. 初始团队和 DAG 主要来自后端固定模板，不是完全由任务构建智能体根据材料动态生成；AI 负责后续调整。
2. 节点成功以 Claude `result` 非错误为准，没有统一验证“指定文件一定存在、测试一定通过、验收条件一定满足”。
3. 服务重启后能恢复任务事实和历史日志，但不能恢复同一个 Claude 模型上下文。
4. 权限模式偏激进，人工权限接口与自动放行策略并存，需要统一安全模型。
5. 文件锁和修订号没有形成跨进程 CAS，默认只能安全运行单实例。
6. Knowledge Base 当前是路径/MCP 元数据和任务快照，不做向量化、召回和排序。
7. ChangeRequest 已能记录和路由，但增量 DAG、缺陷状态自动闭环仍不完整。
8. REST 高频轮询足够本地使用，但规模扩大后应升级推送通道和统一可观测性。

面试中主动说出这些边界，反而能体现你理解了工程现实和演进路线。

## 11. 三分钟面试口述版

“这个项目是一个基于 Claude Code CLI 的多智能体研发编排平台。它不是简单的聊天壳，而是把完整的软件研发过程建模成团队、阶段和 DAG。前端用 React 展示任务、团队拓扑、阶段会话和人工确认；后端是 Go 模块化单体，负责资产版本、任务状态、DAG 调度、文件持久化和 Claude 子进程生命周期。

每个任务目录既是状态容器也是项目工作区。全局 Agent、Skill 和 Rule 在任务启动时按版本冻结并物化到本地，然后每个成员对应一个可复用的 Claude Code 长会话。调度器维护 PENDING、READY、RUNNING、SUCCEEDED、FAILED 等节点状态，按 ALL 或 ANY 依赖解锁后继。需求、架构、原型和最终交付都有人工门禁，可回退的契约和工程骨架可以提前并行，但具体业务不能越过确认点。

Claude 使用 stream-json NDJSON 协议。Go 并发读取 stdout、stderr 和进程退出事件，给事件分配递增序号；React 按游标轮询，只拿增量。当前状态用原子 JSON，历史和协议流用 JSONL/NDJSON，因此服务重启后能从任务目录恢复事实和历史，但不能精确恢复模型内上下文。

这个架构选择 Go 和文件存储，是因为它定位为本地单机控制面，核心难点是进程和文件，而不是大规模业务查询。它的主要演进点是更严格的权限隔离、可验证的节点完成契约、真正的会话恢复、推送式事件以及多实例一致性。”

## 12. 高频追问与回答

### Q1：它和普通 AI 编程助手有什么区别？

普通助手围绕一次会话或一次编码任务；本项目管理完整研发流程，重点是角色分工、依赖调度、人工门禁、过程状态、共享产物和最终验收。

### Q2：多智能体是怎么实现的？

每个任务成员映射为独立 Claude Code CLI 子进程和会话路由。角色 Prompt 与技能不同，模型上下文独立，但所有成员读写同一个任务目录，通过文档、源码和状态文件协作。

### Q3：为什么不是微服务？

当前所有关键资源都在一台宿主机：文件、CLI 进程和项目目录。模块化单体能减少分布式事务、远程进程控制和一致性成本。未来若要远程执行，再把 Runtime Manager 抽成 Worker 更合理。

### Q4：DAG 如何保证正确？

保存前校验唯一节点、合法成员、存在的依赖和无环；运行时只有依赖满足才从 PENDING 变 READY。状态迁移也有白名单，终态不能任意回退，失败节点只允许明确重试或跳过。

### Q5：并行是怎么产生的？

同一时刻所有依赖已经满足、并且符合当前阶段策略的 READY 节点都可以启动。架构契约完成后，前后端骨架可并行；架构和原型确认后，前后端业务开发也可以并行。

### Q6：怎么防止 AI 提前写错方向？

通过阶段门禁和 Prompt 边界限制。需求、架构、原型未确认前，只允许可回退的契约、类型、接口桩和工程骨架提前执行。真正的防线仍需增加产物校验和更严格的权限沙箱。

### Q7：状态为什么同时放 Plan 和 RuntimeState？

Plan 表示可编辑的团队和工作流定义；RuntimeState 表示一次执行中的节点状态和活动会话。定义与运行事实分开，编辑 DAG 时可以迁移现有状态，也避免把高频状态反复写回完整计划。

### Q8：如何保证文件不写坏？

完整 JSON 先写同目录临时文件、刷新并关闭，再原子替换目标文件；追加历史按行独立编码。这样崩溃最多影响最后一条追加记录，不会让读者看到半个 JSON 文档。

### Q9：如何处理多个 Agent 同时完成？

RuntimeState 的读改写由专门互斥锁串行化。每个完成事件更新一个节点后重新计算后继，避免两个 goroutine 用旧快照相互覆盖。

### Q10：会话为什么能复用？

Manager 维护“任务 + 成员 → 最近会话”的索引。同一成员的进程仍 RUNNING 且不 Busy 时，新消息直接写入原 stdin，保留模型上下文并减少启动成本。

### Q11：后端重启后怎么办？

任务、计划、节点状态、配置快照和日志仍在磁盘。页面能展示归档会话，RUNNING 节点在没有活进程时可重新启动。但这不是原会话续传，新进程靠文件和完整 Prompt 重建任务上下文。

### Q12：为什么用轮询？

本地单用户首版优先简单可靠。递增序号让轮询具备断线补拉能力；未来切 WebSocket/SSE 时仍可沿用相同游标语义。

### Q13：如何处理需求变更？

先追加 ChangeRequest，再投递给项目经理做影响分析和责任路由。理想状态是只重开受影响节点，而不是全链路重跑；当前自动闭环还需要增强。

### Q14：部署为什么放在验收之后？

避免未确认的中间版本被误认为正式结果。任务 COMPLETED 后部署器才启动前后端、等待端口就绪、记录 PID、日志和访问地址。

### Q15：这个系统最大的风险是什么？

本地全权限 Agent 对不可信仓库的安全风险、以模型 result 代替真实产物验收的可靠性风险，以及文件型单实例存储的扩展性限制。

### Q16：如果要做成团队 SaaS，先改什么？

先拆分受沙箱保护的远程 Worker，引入身份权限和租户隔离；再把权威状态放进支持事务和乐观锁的数据库，以事件总线连接调度器和 Worker；浏览器改为推送；产物接入对象存储和可验证的验收执行器。

## 13. 阅读项目时建议记住的五个锚点

1. 控制面决定“谁、何时、以什么上下文做什么”，Claude 决定“具体怎样完成”。
2. DAG 状态和任务阶段是两套相关但不同的状态机。
3. 每个 Agent 上下文隔离，任务目录是跨 Agent 的共享事实媒介。
4. 人工门禁保证产品决策不会被后台并行任务越权固化。
5. 当前恢复是文件驱动的任务恢复，不是模型会话的精确续传。
